# Agentic Coding 最佳实践

## 概述

在 Agentic Coding 实践中，提升效率的关键在于优化与 AI 的协作方式，而非寄望于无限的上下文窗口。本章将深入探讨如何理解 LLM 的本质特征，以及如何基于这些理解制定高效的协作策略。

## 第一性原理：理解 LLM 的本质

### LLM 是如何"思考"的

大语言模型的工作方式可以用一句话概括：**预测下一个 token**。

当你向 LLM 提问时，它并不是先在"脑中"构思好完整答案再输出。相反，它每次只做一件事：基于当前看到的所有文本（你的输入 + 它已经生成的内容），预测最可能的下一个词是什么。然后把这个词加入序列，再预测下一个，如此循环直到生成结束。这种方式被称为**自回归生成（Autoregressive Generation）**。

理解这一点至关重要，因为它揭示了 LLM 的几个本质特征：

#### 1. 没有独立于输出的"思考"过程

LLM 的推理就是生成本身。它不能先想好再说，只能边说边想。这就是为什么让模型"一步步思考"（Chain-of-Thought）会提升效果——你实际上是在给它更多的"思考空间"，让它通过生成中间步骤来辅助推理。尽管新一代模型很多都带有显式的 reasoning 能力，依然脱离不了这个范式。

#### 2. 上下文就是全部记忆

LLM 没有独立的记忆存储。它对当前对话的所有"理解"，完全来自于输入给它的上下文窗口。窗口之外的内容，对模型来说就是不存在的。

#### 3. 生成具有概率性

每一步预测都是基于概率分布采样，这意味着同样的输入可能产生不同的输出。

### Attention：LLM 如何"阅读"上下文

在预测下一个 token 时，模型需要从上下文中提取相关信息，这个过程由 **Attention（注意力）机制** 完成。

你可以把 Attention 想象成一个动态的"聚光灯"：当模型生成每个新 token 时，它会扫视整个上下文，对不同位置的内容分配不同的"注意力权重"。权重高的部分会对当前生成产生更大影响，权重低的部分则几乎被忽略。

## 当前 Coding Agent 的局限性

自回归 LLM 的核心工作方式天然带来一些局限，在 Coding Agent 里这些局限会被放大，因为软件开发是"长链路、强约束、强验证"的任务。

### 1. 局部最优：一步一步"续写"，不等于全局规划

- 容易先写得很像、很顺，然后在后面发现不对再补丁式修修补补（历史债务快速累积）
- 多文件重构/架构调整这种"先规划后落地"的任务，会变成边写边想，导致接口不一致、重复实现、遗漏迁移步骤
- 对"最终能不能通过测试/CI"缺乏感知，除非你把测试结果显式喂回 agent 循环

### 2. 一旦走偏，会沿着偏差继续滚雪球

- 早期误读需求/误判代码库的约束，导致后面每一步都在错误世界观里自洽
- 生成了一个不存在的函数名/类型后，后续会越来越"相信它存在"，直到编译/运行时发现错误
- 在长对话、长任务里尤其明显：越写越像"另一个项目"

### 3. 输出是流式的，无法回头修改之前输出的内容

- 擅长"写新文件/新段落"，相对不擅长在复杂代码中做精确、最小化、局部一致的编辑
- 容易倾向于"重写一遍"而不是"进行修改"，导致 diff 过大、review 成本高
- 在需要保持大量不变量（API、格式、风格、兼容性）的仓库里尤其痛苦

### 4. 满足约束的能力有限，而代码是强语法/强语义约束的

- "看起来合理"的实现，经常在边界条件、并发、错误处理、资源释放上出错
- 跨文件的符号解析、泛型/模板推导、宏/代码生成等，靠纯文本推断很容易漏
- 复杂的重构（rename、move、split）没有 AST/语义工具辅助时，错一个引用就全盘崩

### 5. 天然单线程思考，难并行探索

- 在方案选择（架构、依赖、实现路径）上容易早早押注一个方向，缺少系统性对比
- 排查 bug 时更像"单线推理"，不如人类/工具那样并行假设、并行验证

## 核心策略：短对话、精简上下文

基于对 LLM 本质的理解，最有效的协作策略是采用"短对话、精简上下文"的模式：

### 1. 将复杂任务拆解为专注的子对话

**原则**: 不要试图在一个超长对话中完成所有事情

**最佳实践**:
- 每个对话专注于一个明确的子任务
- 在对话开始时提供必要的上下文，而非依赖历史
- 任务完成后开启新对话，避免上下文污染

**示例**:
```
❌ 不推荐：在一个对话中完成"重构整个用户模块"

✅ 推荐：拆分为多个专注对话
- 对话1：分析当前用户模块的结构和问题
- 对话2：设计新的接口和数据结构
- 对话3：实现用户认证功能
- 对话4：实现用户权限管理
- 对话5：编写测试用例
```

### 2. 主动管理上下文内容

**原则**: 上下文是 LLM 的全部记忆，要精心选择放入什么

**最佳实践**:
- 只提供与当前任务直接相关的代码和文档
- 使用摘要替代完整内容（当内容过长时）
- 明确告诉模型哪些约束是必须遵守的

**示例**:
```
❌ 不推荐：
"这是整个项目的代码，请修复第 1000 行的 bug"

✅ 推荐：
"以下是相关的3个文件片段和错误日志：
- UserService.java 第 95-120 行（问题发生处）
- User.java 的接口定义
- 完整的错误堆栈
请分析并修复这个空指针异常"
```

### 3. 利用结构化的任务模板

**原则**: 清晰的结构帮助模型理解任务边界

**任务模板示例**:
```markdown
## 任务
[简洁描述要完成的任务]

## 上下文
[必要的背景信息和代码片段]

## 约束
- [必须遵守的规则1]
- [必须遵守的规则2]

## 期望输出
[明确说明需要什么样的输出]
```

## 复利工程：将经验沉淀为可复用知识

"复利工程"是一种将日常开发经验（bug 修复、代码审查、问题排查等）沉淀为可复用项目知识库的方法，使系统获得"记忆"并实现效率的持续增长。

### 1. 建立项目知识库

**内容类型**:
- **编码规范**: 项目特定的命名、格式、架构规范
- **常见问题**: 经常遇到的 bug 模式和解决方案
- **设计决策**: 为什么选择某种架构或技术
- **环境配置**: 开发、测试、部署的标准流程

**示例**:
```markdown
# 项目知识库

## 编码规范
- 所有 API 响应使用统一的 ResponseWrapper 封装
- 异常处理必须包含业务错误码
- 数据库字段使用 snake_case，代码中使用 camelCase

## 常见问题
### 问题：用户会话过期导致 500 错误
**原因**: Redis 连接超时未正确处理
**解决**: 使用 SessionManager.safeGet() 替代直接访问

## 设计决策
### 为什么使用事件驱动架构？
- 需求：解耦订单和库存服务
- 考虑的方案：直接调用、消息队列、事件总线
- 最终选择：事件总线，因为...
```

### 2. 将知识库融入 AI 协作流程

**策略**:
- 在每次对话开始时，提供相关的知识库片段
- 发现新的模式或问题时，及时更新知识库
- 定期回顾和整理知识库内容

**效果**:
- AI 能够遵循项目特定的规范
- 避免重复犯同样的错误
- 新团队成员（包括 AI）能快速上手

## 改善开发者体验的双重价值

改善开发者体验（Developer Experience, DX）具有双重价值：既能帮助人类开发者，也能显著提升 AI 的表现。

### 1. 清晰的文档

**对人的价值**: 降低理解成本，减少沟通
**对 AI 的价值**: 提供准确的上下文，减少幻觉

**最佳实践**:
- 在代码中添加清晰的注释，解释"为什么"而非"是什么"
- 维护最新的 README 和架构文档
- 为复杂逻辑编写设计文档

### 2. 快速的反馈循环

**对人的价值**: 快速验证，提高迭代速度
**对 AI 的价值**: 快速发现错误，避免错误累积

**最佳实践**:
- 编写快速运行的单元测试
- 配置即时的 linting 和类型检查
- 使用热重载加速开发循环

### 3. 一致的代码结构

**对人的价值**: 降低认知负担，提高可维护性
**对 AI 的价值**: 更容易理解模式，生成一致的代码

**最佳实践**:
- 使用统一的项目模板和脚手架
- 建立清晰的目录结构规范
- 强制执行代码风格（使用格式化工具）

## 刻意练习：成为驾驭 AI 的专家

与 AI 的协作应被视为一门需要刻意练习的技能。通过不断实践，开发者可以成为驾驭 AI 的"专家型通才"，在更广阔的领域创造价值。

### 1. 练习任务拆解

**目标**: 能够快速将复杂任务拆解为适合 AI 处理的子任务

**练习方法**:
- 面对新任务时，先思考如何拆分
- 记录哪些拆分方式效果好
- 总结拆分的通用模式

### 2. 练习上下文管理

**目标**: 能够精准判断需要提供哪些上下文

**练习方法**:
- 尝试用最少的上下文完成任务
- 当 AI 出错时，分析是否因为上下文不足
- 建立"上下文清单"模板

### 3. 练习结果验证

**目标**: 能够快速发现 AI 输出中的问题

**练习方法**:
- 建立审查清单（语法、逻辑、安全、性能）
- 运行测试验证功能正确性
- 进行代码审查发现潜在问题

### 4. 练习知识沉淀

**目标**: 将每次协作中学到的经验转化为可复用的知识

**练习方法**:
- 每次修复 bug 后，思考是否可以预防
- 发现好的 prompt 模式时，记录下来
- 定期回顾和整理积累的知识

## 实战案例

### 案例1：使用短对话完成代码重构

**任务**: 将一个 500 行的单文件模块拆分为多个小模块

**传统方式**（❌ 不推荐）:
```
在一个对话中：
"请帮我重构这个文件，拆分成多个小模块"
[粘贴 500 行代码]

结果：AI 容易迷失在长代码中，可能遗漏关键依赖
```

**短对话方式**（✅ 推荐）:
```
对话1：
"分析这段代码的结构，列出主要的功能块和它们之间的依赖关系"
[粘贴代码]

对话2：
"基于以下分析结果，设计模块拆分方案"
[粘贴对话1的分析结果]

对话3：
"根据设计方案，创建 UserAuthentication 模块"
[粘贴相关代码片段和设计方案]

对话4：
"创建 UserPermission 模块，需要引用 UserAuthentication"
[粘贴相关代码和接口定义]

...以此类推
```

### 案例2：利用知识库避免重复问题

**场景**: 项目中经常出现日期时区处理错误

**解决方案**:
1. 在知识库中记录问题和解决方案
2. 每次涉及日期处理时，提供知识库片段给 AI

**知识库条目**:

> ## 日期时区处理规范
>
> ### 问题
> 日期在前后端传递时经常出现时区错误，导致显示不正确
>
> ### 规范
> 1. 后端存储和传递一律使用 UTC 时间
> 2. 前端显示时根据用户时区转换
> 3. API 传递使用 ISO 8601 格式：`2024-01-15T10:30:00Z`
>
> ### 代码示例（Java）
> - 正确：`Instant now = Instant.now();` // UTC
> - 正确：`DateTimeFormatter.ISO_INSTANT.format(now);`
> - 错误：`Date now = new Date();` // 本地时区

**使用方式**:
```
"请实现订单创建功能，以下是日期处理规范：
[粘贴知识库条目]

请确保日期处理符合规范"
```

## 总结

在 Agentic Coding 时代，与 AI 高效协作的关键不在于期望更强大的模型或更长的上下文窗口，而在于：

1. **理解 LLM 的本质**：自回归生成、上下文即记忆、概率性输出
2. **采用正确的协作策略**：短对话、精简上下文、任务拆解
3. **建立知识复用机制**：沉淀经验、构建知识库、持续改进
4. **改善开发者体验**：清晰文档、快速反馈、一致结构
5. **刻意练习协作技能**：任务拆解、上下文管理、结果验证、知识沉淀

通过这些实践，开发者可以最大化 AI 协作的效率，同时避免常见的陷阱，成为驾驭 AI 的"专家型通才"。
